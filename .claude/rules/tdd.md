# TDD Rule

> **이 규칙은 Rigid다 — 상황에 맞게 변형하지 마라.** 예외가 필요하다고 판단되면 규칙을 어기지 말고 사용자에게 먼저 확인하라.

## 0. 우선순위 (Fallback 조항)

이 파일은 **기본값(fallback)** 이다. 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 **그 규칙이 이 파일보다 우선**한다. 프로젝트 규칙이 없거나 TDD 적용 여부를 언급하지 않을 때만 이 파일을 따른다.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API 엔드포인트 / 핸들러**
- **유틸리티 함수** (순수 함수, 파서, 포매터 등)
- **버그 수정** (재현 테스트를 먼저 작성 — 실패를 재현하지 못하면 수정도 검증할 수 없다)

### TDD가 불필요한 대상

- **타입 정의** (인터페이스, 타입 별칭 — 컴파일러가 검증)
- **설정 파일** (`tsconfig.json`, `eslint.config.js` 등)
- **순수 UI 마크업/스타일** (동작 로직이 없는 렌더링 전용 컴포넌트, CSS)
- **SQL / 마이그레이션 스크립트**

판단이 애매한 대상(예: 로직이 섞인 컴포넌트)은 **로직 부분만 분리해 순수 함수로 만들고 그 함수에 TDD를 적용**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작(behavior) = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 마라.
- 테스트를 작성한 즉시 **반드시 실행해서 실패를 확인**한다. 실행하지 않고 다음 단계로 넘어가는 것은 금지.
- 실패 이유는 반드시 **"기능이 아직 구현되지 않음"** 이어야 한다. 문법 오류, 타입 오류, import 누락 등으로 인한 실패는 RED가 아니다 — 먼저 그 오류부터 고쳐라.

### GREEN

- 테스트를 통과시키는 데 **필요한 최소한의 코드만** 작성한다 (YAGNI).
- 아직 요구되지 않은 케이스, 파라미터, 확장 포인트를 미리 만들지 마라.
- 구현 후 **신규 테스트와 기존 테스트 전체가 통과**하는지 확인한다. 신규 테스트만 확인하고 넘어가는 것은 금지.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출 등 **구조 개선만** 수행한다.
- 매 변경 후 테스트가 **green으로 유지**되는지 확인한다.
- 이 단계에서 **새로운 동작을 추가하지 마라.** 새 동작이 필요하면 다음 사이클의 RED로 넘어간다.

### 반복

REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 모든 동작을 커버할 때까지 반복.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다는 사실을 발견하면 **그 코드를 삭제하고 RED부터 다시 시작**한다.
- "일단 참고용으로 남겨두고 테스트만 나중에 맞추는" 방식은 **금지**한다. 순서를 어긴 코드는 예외 없이 삭제 대상이다.

## 4. 변명 차단표

아래 변명이 나오면(자신의 판단이든 사용자 요청이든) 규칙을 우회하지 말고 다음 반론으로 대응한다.

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 로직일수록 테스트 작성 비용도 낮다. 단순하다는 판단 자체가 틀렸을 때 테스트 없이는 그 사실을 알 수 없다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. 코드가 존재하는 시점에 테스트가 없으면 검증되지 않은 코드가 그대로 배포된다. |
| "시간이 없다" | 테스트 없이 짠 코드는 디버깅 시간으로 그 이상을 되갚는다. RED-GREEN-REFACTOR는 우회 경로가 아니라 더 빠른 경로다. |
| "삭제하면 낭비" | 순서를 어기고 작성한 코드는 검증되지 않은 코드다. 매몰비용을 이유로 검증되지 않은 코드를 남기지 마라. |
| "프로토타입이다" | 프로토타입은 십중팔구 그대로 프로덕션에 남는다. 프로토타입이라는 이유로 규칙을 면제하지 마라. |
