# commit: 변경사항 분석 후 컨벤션 커밋

현재 git 저장소의 변경사항을 분석하여 논리적 단위로 나누고, 컨벤션에 맞는 한국어 커밋 메시지를 작성해 **사용자 승인 없이 바로 커밋**한다.

## 워크플로우

### Step 1: 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

- `git status` — 추적되지 않은 파일 포함 전체 변경 파일 목록 확인
- `git diff` — 스테이징되지 않은 변경사항 확인
- `git diff --staged` — 이미 스테이징된 변경사항 확인
- `git log --oneline -10` — 기존 커밋 메시지 스타일이 있으면 참고(없으면 아래 컨벤션을 기본값으로 사용)

새로 생성된 파일(untracked)도 내용을 읽어 어떤 변경인지 파악한다.

### Step 2: 논리적 단위로 분류

변경된 파일들을 의미 단위로 묶는다. 예:

- 기능 추가와 관련 없는 설정 변경(예: `.gitignore`, `package.json` 의존성 추가)은 별도 커밋으로 분리한다.
- 서로 관련 없는 여러 기능이 섞여 있으면 각각 별도 커밋으로 나눈다.
- 연관된 파일(예: 컴포넌트 + 해당 테스트, 타입 정의)은 하나의 커밋으로 묶는다.

### Step 3: 한국어 커밋 메시지 작성

각 논리 단위마다 다음 형식으로 메시지를 작성한다.

```
<type>: <한국어 요약>
```

`type`은 변경의 성격에 따라 다음 중 하나를 사용한다:

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변경 없는 코드 구조 개선
- `chore`: 빌드/설정/의존성 등 잡무성 변경
- `docs`: 문서 변경
- `test`: 테스트 추가/수정
- `style`: 포맷팅 등 스타일 변경(로직 변경 없음)

요약은 **무엇을 왜** 바꿨는지 한 문장으로 간결하게 작성한다. "~함", "~추가" 등 개조식 어미를 사용하고, 불필요한 설명이나 마침표는 붙이지 않는다. 본문이 필요한 큰 변경은 요약 아래 빈 줄을 두고 상세 내용을 덧붙인다.

### Step 4: 자동 커밋 실행

사용자 승인을 받지 않고 바로 진행한다.

1. 각 논리 단위별로 관련 파일만 `git add <파일...>`로 스테이징한다(`git add -A`/`git add .` 금지 — 의도치 않은 파일 포함 방지).
2. 스테이징 결과를 `git status`로 다시 확인해 의도한 파일만 포함됐는지 검증한다.
   - `.env`, `credentials.json` 등 **시크릿을 담고 있을 수 있는 파일**이 포함돼 있으면 이 경우만 예외적으로 커밋을 멈추고 내용을 확인한 뒤 사용자에게 알린다.
   - 그 외에는 확인 질문 없이 계속 진행한다.
3. 커밋 메시지는 HEREDOC으로 전달해 포맷을 보존한다.
4. 각 논리 단위마다 위 과정을 반복해 순서대로 커밋한다.
5. 전체 커밋 완료 후 `git log --oneline -n <커밋 수>`와 `git status`로 결과를 확인해 요약 보고한다.

## 주의사항

- `git commit --amend`, `git push --force` 등 파괴적/이력 변경 작업은 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.
- pre-commit 훅이 실패하면 원인을 분석해 수정한 뒤 새 커밋을 생성한다(`--no-verify`로 우회하지 않는다).
- 커밋 메시지는 한국어로 작성하되, 코드 식별자·기술 용어는 원문 그대로 유지한다.
